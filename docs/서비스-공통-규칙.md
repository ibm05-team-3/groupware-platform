# pooled 테넌트 + IAM 관련 규칙

출처: https://coliving-platform.atlassian.net/wiki/spaces/hrpayrolla/pages/26345473/pooled+IAM

## 1. IAM 권한 규칙

- IAM 권한은 **서비스 API 기준**으로 나눠 줍니다.
- 권한 명명 방식: `서비스명:API명` (예: `hr:createEmployee`, `payroll:viewPayslip`)
- API 게이트웨이는 **큰 권한(coarse-grained)**만 비교합니다. 세부 권한 판단은 각 서비스에서 수행합니다.

JWT 예시

```json
{
  "iss": "user-service",
  "sub": "123",
  "tenant_id": "00000000-0000-0000-0000-000000000001",
  "roles": ["root"],
  "permissions": ["hr:*", "payroll:read"]
}
```

- 프론트엔드에서는 권한 별로 메뉴를 보이거나 숨깁니다.
- 로그인/테넌트 선택 시 한 번 받아서 메모리에 들고 있음
- 권한이 바뀌는 이벤트(테넌트 전환, 관리자가 역할 변경 등)가 있을 때 다시 받아옴
- 메뉴는 그 데이터로 조건부 렌더링
- **페이지를 열 때마다 요청하지 않음**

### 권한 체크 절대 원칙

- 클라이언트가 보내는 tenant_id나 role 정보는 신뢰하지 않습니다.

## 2. Pooled 테넌트 구조 규칙

Pooled 테넌트(Shared Schema + tenant_id) 구조에서는 팀원들이 반드시 지켜야 할 규칙이 있습니다. 안 지키면 테넌트 간 데이터 유출이 바로 발생합니다.

### 필수 규칙

1. **모든 쿼리에 tenant_id 조건을 넣는다**
   - SELECT, UPDATE, DELETE 모두 WHERE tenant_id = :current_tenant를 기본으로 한다.
   - 또는 엔티티에 Hibernate @Filter 방식을 고려하세요.
2. **tenant_id는 클라이언트가 보내는 값을 믿지 않는다**
   - 요청 바디나 쿼리 파라미터로 받은 tenant_id를 그대로 쓰면 안 됨.
   - 반드시 인증된 세션/토큰에서 꺼낸 테넌트 ID만 사용.
3. **유니크 제약은 (tenant_id, xxx) 조합으로 건다**

```sql
-- 잘못된 예
UNIQUE (email)

-- 올바른 예
UNIQUE (tenant_id, email)
```

4. **외래키도 테넌트 일관성을 고려한다**
   - 가능하면 복합 외래키로 테넌트 경계를 넘지 못하게 막는다.
   - 예: (tenant_id, user_id) 형태로 참조.
5. **인덱스에 tenant_id를 앞에 둔다**

```sql
CREATE INDEX ON orders (tenant_id, created_at);
CREATE INDEX ON users (tenant_id, email);
```

6. **크로스 테넌트 쿼리는 명시적으로만 허용**
   - 일반 애플리케이션 코드에서 테넌트 필터 없는 쿼리 금지.
   - 관리자/통계용 쿼리는 별도 권한과 코드 경로로 분리.
7. **캐시 키에 tenant_id를 포함한다**

```text
cache_key = f"tenant:{tenant_id}:user:{user_id}"
```

8. **백그라운드 작업도 테넌트 컨텍스트를 명시한다**
   - Job 실행 시 반드시 tenant_id를 파라미터로 받고, 그 안에서만 동작하게 한다.
9. **테스트 시 테넌트 격리를 검증한다**
   - A 테넌트 데이터로 B 테넌트가 조회/수정 못 하는지 테스트 케이스를 반드시 작성.
10. **Raw SQL 사용 시 특히 주의**
    - ORM을 쓰더라도 raw query나 복잡한 쿼리에서는 tenant_id 누락이 자주 발생함.

### 추가로 권장하는 것

| 항목 | 내용 |
| --- | --- |
| RLS 사용 | PostgreSQL이라면 Row Level Security를 켜서 DB 레벨에서 한 번 더 막기 |
| 테넌트 컨텍스트 미들웨어 | 요청 초반에 테넌트 ID를 컨텍스트에 심어두고, 이후 코드에서는 그걸 사용 |
| 코드 리뷰 체크리스트 | “이 쿼리에 tenant_id 있나?”를 PR 리뷰 필수 항목으로 넣기 |
| 신규 테이블 생성 시 | tenant_id 컬럼 + 인덱스 + (필요시) RLS 정책을 기본 템플릿으로 제공 |

### 한 줄 요약

> Pooled 구조에서는 tenant_id를 빼먹는 순간 다른 회사 데이터가 보인다. 모든 쿼리, 캐시, 잡에 테넌트를 명시하고, 클라이언트가 준 tenant_id는 절대 믿지 마라.

## 3. SQL 테이블 공통 컬럼

- 필요한 테이블에 생성·수정 일시 컬럼 `created_at`, `updated_at`(TIMESTAMPTZ)을 둡니다.
- 엔티티는 공통 클래스 `BaseTimeEntity`를 상속합니다.
  - `created_at`: 생성 시 자동 기록
  - `updated_at`: 수정 시 자동 갱신

```java
@Getter
@MappedSuperclass
public abstract class BaseTimeEntity {

    @CreationTimestamp
    @Column(name = "created_at")
    protected OffsetDateTime createdAt;

    @UpdateTimestamp
    @Column(name = "updated_at")
    protected OffsetDateTime updatedAt;
}
```
