# pooled 테넌트 + IAM 구조로 만들기 위한 규칙

## 1. 권한

- 각 서비스의 API 권한 이름은 `서비스명:API명`입니다. 예: `hr:createEmployee`, `payroll:viewPayslip`.
- 요청의 통과 여부는 JWT 액세스 토큰의 `permissions`로 판단합니다. user-service에 권한을 다시 묻지 않습니다.
- 토큰을 받는 서비스는 user-service 공개 키와 동일한 값을 가지고 서명, 발급자, 만료를 직접 확인합니다. 비밀 키는 user-service만 가집니다. 게이트웨이의 서명 확인으로 이 검사를 대신하지 않습니다.
- API 게이트웨이는 `context`로 본사(`platform`), 로그인한 회사 밖(`account`), 회사 안(`tenant`)만 구분합니다. `hr:*` 같은 판단은 각 서비스가 합니다.
- 화면이 메뉴를 숨겨도 권한 검사가 아닙니다. 통과 여부는 각 서비스가 토큰으로 판단합니다.

JWT 예시

회사 안. `context`는 `tenant`입니다. 그 테넌트 하나의 권한만 있습니다.

```json
{
  "iss": "user-service",
  "sub": "00000000-0000-0000-0000-000000000001",
  "context": "tenant",
  "tenant_id": "00000000-0000-0000-0000-000000000001",
  "permissions": ["hr:*", "payroll:read"]
}
```

로그인한 회사 밖. `context`는 `account`입니다. 계정, 회사 목록에 씁니다. 회사 데이터와 본사 API는 열리지 않습니다.

```json
{
  "iss": "user-service",
  "sub": "00000000-0000-0000-0000-000000000001",
  "context": "account",
  "permissions": []
}
```

본사. `context`는 `platform`입니다. `tenant_id`가 없고, 본사 역할의 `permissions`만 있습니다.

```json
{
  "iss": "user-service",
  "sub": "00000000-0000-0000-0000-000000000001",
  "context": "platform",
  "permissions": ["user:listMembers"]
}
```

- 토큰에는 역할 코드를 넣지 않습니다. `context`는 `account`, `platform`, `tenant` 중 하나입니다. 게이트웨이가 이 값으로 경로를 구분합니다. 각 서비스의 API 통과 조건은 `permissions`와 `tenant_id`입니다.
- `tenant_id`가 있으면 그 테넌트 하나의 권한만 들어 있습니다. 테넌트 데이터는 이 클레임이 있는 토큰만 다룹니다.
- 다른 테넌트의 권한은 같은 토큰에 없습니다. 테넌트나 권한이 바뀌면 새 토큰이 다시 발급됩니다.
- `account`와 `platform`에는 `tenant_id`가 없습니다. `account`의 `permissions`는 빈 목록입니다. 본사 기능은 `platform` 토큰의 `permissions`로 판단합니다.
- 회원 이메일 로그인은 `POST /user/login`입니다. `account` 토큰만 발급합니다. `permissions`는 빈 목록입니다.
- 회사 선택은 `POST /user/tenant-entry`입니다. 본문 `tenant`는 회사 slug이고, 그 세션의 토큰을 `context`가 `tenant`인 그 회사 토큰으로 바꿉니다. 본사 권한은 복사하지 않습니다.
- `permissions`에 각 서비스의 값이 있을 때만 그 API를 엽니다. `hr:*`는 hr 서비스 안에서만 통합니다. 루트에게 열 API도 `permissions`에 담겨 옵니다.
- 클라이언트가 보내는 `tenant_id`, `role`, `permission`은 신뢰하지 않습니다. 테넌트는 토큰의 `tenant_id`만 사용합니다.

### 역할이 필요할 때

`roles`, `user_platform_roles`, `user_tenant_roles`는 user-service가 넣습니다. 다른 서비스는 이 테이블에 쓰지 않습니다.

새 API를 역할에 넣어야 하면 user-service에 아래 형태로 요청합니다.

```sql
INSERT INTO roles (code, scope, permissions, created_at, updated_at)
VALUES ('payroll_reader', 'TENANT', ARRAY['payroll:read'], now(), now());
```

- `code`는 50자 이내의 역할 코드입니다. 한 코드는 하나의 `scope`만 가집니다.
- 본사에 줄 역할은 `scope`를 `PLATFORM`으로, 테넌트 안에서 줄 역할은 `TENANT`로 요청합니다.
- `permissions`는 비어 있지 않은 `서비스명:API명` 배열입니다. `hr:*`처럼 와일드카드는 API 자리에만 쓰고, 그 서비스 안에서만 적용됩니다.
- `root`는 역할 코드로 요청하지 않습니다.
- 회원에게 역할을 붙이는 작업도 user-service가 합니다. 본사 역할은 `user_platform_roles`, 테넌트 역할은 `user_tenant_roles`입니다.

## 2. 각 서비스의 테넌트 데이터

Pooled 테넌트(Shared Schema + tenant_id)에서는 각 서비스 테이블이 아래를 지켜야 합니다. 빠지면 다른 회사 데이터가 보입니다.

로그인 계정은 각 서비스 테이블이 아닙니다. `users`에는 `tenant_id`가 없고, 이메일이 있으면 전역으로 유일합니다. 회사 소속은 user-service의 `user_tenant_memberships`에 있습니다.

### 필수 규칙

1. **모든 쿼리에 토큰의 tenant_id 조건을 넣는다**
   - SELECT, UPDATE, DELETE 모두 `WHERE tenant_id = :토큰의 tenant_id`를 기본으로 한다.
   - 또는 엔티티에 Hibernate `@Filter` 방식을 고려하세요.
2. **요청에 실린 tenant_id는 쓰지 않는다**
   - 바디나 쿼리 파라미터의 `tenant_id`로 조회·수정하지 않습니다.
   - JWT 액세스 토큰의 `tenant_id`만 사용합니다.
3. **테넌트 안 데이터의 유니크는 (tenant_id, …)로 건다**

```sql
-- 예: 사번
UNIQUE (tenant_id, employee_number)
```

4. **외래키도 테넌트 일관성을 고려한다**
   - 가능하면 복합 외래키로 테넌트 경계를 넘지 못하게 막는다.
   - 예: `(tenant_id, user_id)` 형태로 참조.
5. **테넌트 소속 테이블의 인덱스는 tenant_id를 앞에 둔다**

```sql
CREATE INDEX ON payslips (tenant_id, created_at);
CREATE INDEX ON employees (tenant_id, employee_number);
```

6. **크로스 테넌트 쿼리는 명시적으로만 허용**
   - 일반 애플리케이션 코드에서 테넌트 필터 없는 쿼리 금지.
   - 본사 통계처럼 회사가 여럿인 조회는 별도 권한과 코드 경로로 분리한다. 그 경로는 `tenant_id`가 없는 본사 토큰의 `permissions`로 연다.
7. **캐시 키에 tenant_id를 포함한다**

```text
cache_key = f"tenant:{tenant_id}:user:{user_id}"
```

8. **백그라운드 작업도 테넌트 컨텍스트를 명시한다**
   - Job 실행 시 반드시 `tenant_id`를 파라미터로 받고, 그 안에서만 동작하게 한다.
9. **테스트 시 테넌트 격리를 검증한다**
   - A 테넌트 데이터로 B 테넌트가 조회·수정하지 못하는지 테스트 케이스를 반드시 작성한다.
10. **Raw SQL 사용 시 특히 주의**
    - ORM을 쓰더라도 raw query나 복잡한 쿼리에서는 `tenant_id` 누락이 자주 발생한다.
11. **행은 (tenant_id, id)로 읽는다**
    - id만 찾은 뒤 테넌트를 비교하지 않습니다.
    - 토큰의 테넌트에 없는 행은 없는 자원으로 응답합니다.
12. **다른 서비스를 부를 때는 그 사용자의 JWT 액세스 토큰을 전달한다**
    - 브라우저가 보내는 것은 세션 쿠키입니다. 게이트웨이는 WebFlux라 `WebClient`로 user-service의 `/internal/session/access`를 호출해 액세스 토큰을 받고, `Authorization: Bearer <액세스 토큰>` 헤더를 만들어 서비스로 넘깁니다. 이미 `Bearer`가 있으면 그 값을 바꾸지 않습니다.
    - 받을 때는 이 헤더만 봅니다. 각 서비스가 가진 user-service 공개 키로 ES256 서명, 발급자, 만료를 확인하고, 테넌트와 권한은 클레임의 `tenant_id`와 `permissions`만 사용합니다. 게이트웨이를 통과했다는 이유로 이 검사를 생략하지 않습니다.
    - 다른 서비스를 호출할 때는 받은 `Authorization` 헤더를 그대로 전달합니다. 토큰을 새로 만들거나, 테넌트 조건이 없는 내부 계정으로 바꾸지 않습니다.
    - 서비스 사이 동기 호출은 `RestClient`와 `@HttpExchange`로 합니다. 경로와 인자는 인터페이스에 적고, 주소는 Eureka에 등록된 서비스 이름을 씁니다. 비동기 호출은 Kafka를 씁니다.
13. **메시지, 검색 문서, 파일 경로에도 토큰의 tenant_id를 넣는다**
    - Kafka 메시지, Elasticsearch 문서, 파일 경로는 SQL과 같은 테넌트 경계를 가집니다.
14. **RLS를 켠 커넥션은 풀로 돌아가기 전에 테넌트 설정을 지운다**
    - 설정이 남으면 다음 요청이 이전 회사 권한으로 실행됩니다.

### 추가로 권장하는 것

| 항목 | 내용 |
| --- | --- |
| RLS 사용 | PostgreSQL이라면 Row Level Security를 켜서 DB 레벨에서 한 번 더 막기. 커넥션을 풀에 반환하기 전에 테넌트 설정을 지운다 |
| 테넌트 컨텍스트 | 요청 초반에 토큰의 `tenant_id`를 컨텍스트에 심어두고, 이후 코드에서는 그걸 사용 |
| 코드 리뷰 체크리스트 | “이 쿼리에 토큰의 tenant_id가 있나?”를 PR 리뷰 필수 항목으로 넣기 |
| 신규 테이블 생성 시 | `tenant_id` 컬럼 + 인덱스 + (필요시) RLS 정책을 기본 템플릿으로 제공 |
