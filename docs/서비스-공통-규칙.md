# pooled 테넌트 + IAM 구조로 만들기 위한 규칙

## 1. 권한

- 권한 이름은 `서비스명:API명`입니다. 예: `hr:createEmployee`, `payroll:viewPayslip`. `hr:*`는 그 서비스 안에서만 통하고, 와일드카드는 API 자리에만 씁니다.
- API 통과는 토큰의 `permissions`로 판단합니다. user-service에 다시 묻지 않습니다.
- 공개 키로 ES256 서명, 발급자, 만료를 확인합니다. 비밀 키는 user-service만 가집니다. 게이트웨이 검사로 대신하지 않습니다.
- 브라우저가 보내는 것은 세션 쿠키입니다. 게이트웨이가 `Authorization: Bearer`로 바꿔 넘깁니다. 이미 `Bearer`가 있으면 바꾸지 않습니다.
- 클라이언트가 보낸 `tenant_id`, `role`, `permission`은 쓰지 않습니다.
- 메뉴를 숨겨도 권한 검사가 아닙니다.

게이트웨이는 `context`가 `platform`인 토큰만 `/*/platform/**`에 통과시킵니다. `POST /*/platform/login`과 본사 OAuth 시작은 빠집니다. `account`와 `tenant`는 경로로 나누지 않습니다.

`context`는 `tenant`, `account`, `platform`입니다.

회사 안. 그 테넌트 하나의 권한만 있습니다.

```json
{
  "iss": "user-service",
  "sub": "00000000-0000-0000-0000-000000000001",
  "context": "tenant",
  "tenant_id": "00000000-0000-0000-0000-000000000001",
  "permissions": ["hr:*", "payroll:read"]
}
```

회사 밖. `permissions`는 빈 목록이고 `tenant_id`가 없습니다.

```json
{
  "iss": "user-service",
  "sub": "00000000-0000-0000-0000-000000000001",
  "context": "account",
  "permissions": []
}
```

본사. `tenant_id`가 없고, 본사 `permissions`만 있습니다.

```json
{
  "iss": "user-service",
  "sub": "00000000-0000-0000-0000-000000000001",
  "context": "platform",
  "permissions": ["user:listMembers"]
}
```

- 다른 테넌트의 권한은 같은 토큰에 없습니다. 테넌트나 권한이 바뀌면 새 토큰이 다시 발급됩니다.

### 역할이 필요할 때

`roles`, `user_platform_roles`, `user_tenant_roles`는 user-service만 넣습니다.

새 API를 역할에 넣어야 하면 아래 형태로 요청합니다.

```sql
INSERT INTO roles (code, scope, permissions, created_at, updated_at)
VALUES ('payroll_reader', 'TENANT', ARRAY['payroll:read'], now(), now());
```

- `code`는 50자 이내이고, 하나의 `scope`만 가집니다.
- 본사는 `PLATFORM`, 테넌트 안은 `TENANT`입니다.
- `permissions`는 비어 있지 않은 `서비스명:API명` 배열입니다.
- `root`는 역할 코드로 요청하지 않습니다.
- 회원에게 역할을 붙이는 것도 user-service가 합니다. 본사는 `user_platform_roles`, 테넌트는 `user_tenant_roles`입니다.

## 2. 테넌트 데이터

회사 데이터는 `tenant_id`로 회사를 가릅니다. `users`는 각 서비스 테이블이 아닙니다. 이메일이 있으면 전역으로 유일하고, 회사 소속은 `user_tenant_memberships`에 있습니다.

1. 조회, 수정, 삭제에 `WHERE tenant_id = :토큰의 tenant_id`를 넣습니다. Hibernate `@Filter`로 넣어도 됩니다.
2. 바디나 쿼리의 `tenant_id`는 쓰지 않습니다.
3. 유니크는 `(tenant_id, …)`입니다. 예: `UNIQUE (tenant_id, employee_number)`.
4. 외래키에 테넌트를 넣습니다. 예: `(tenant_id, user_id)`.
5. 인덱스는 `tenant_id`를 앞에 둡니다. 예: `(tenant_id, created_at)`.
6. 테넌트 조건 없는 조회는 본사 경로로만 둡니다. `tenant_id`가 없는 본사 토큰의 `permissions`로 엽니다.
7. 캐시 키에 `tenant_id`를 넣습니다. 예: `tenant:{tenant_id}:user:{user_id}`.
8. 배치는 `tenant_id`를 받아 그 안에서만 실행합니다.
9. A 회사 데이터로 B 회사가 조회·수정하지 못하는 테스트를 작성합니다.
10. Raw SQL에도 `tenant_id`를 넣습니다.
11. 행은 `(tenant_id, id)`로 읽습니다. 그 테넌트에 없으면 없는 자원으로 응답합니다.
12. Elasticsearch 문서와 파일 경로에도 토큰의 `tenant_id`를 넣습니다.
13. RLS를 켠 커넥션은 풀에 반환하기 전에 테넌트 설정을 지웁니다.

## 3. 서비스 간 통신

- 다른 서비스를 부를 때 받은 `Authorization`을 그대로 넘깁니다. 토큰을 새로 만들거나 내부 계정으로 바꾸지 않습니다.
- 동기 호출은 `RestClient`와 `@HttpExchange`를 쓰고, 주소는 Eureka 서비스 이름입니다.
- 비동기는 Kafka입니다. 메시지에는 토큰의 `tenant_id`를 넣습니다.

### 권장

- PostgreSQL이면 RLS로 한 번 더 막습니다.
- 요청 초반에 토큰의 `tenant_id`를 컨텍스트에 두고, 이후에는 그것을 씁니다.
- PR에서 쿼리에 토큰의 `tenant_id`가 있는지 확인합니다.
- 새 테이블은 `tenant_id`, 그 인덱스, 필요하면 RLS를 기본으로 둡니다.
